# 化妆品企业产品展示平台 V1 — 开发设计评审

## 评审结论

**建议通过设计评审，等待产物确认。** 本轮补足了固定配置的唯一定位、草稿与发布的校验差异、私有资源的访问范围，以及预览和中断的验收判据。优先抽查两件事：后台和 H5 是否始终对同一配置条目取数，以及失去权限或请求顺序错乱时是否还会显示不该显示的草稿。本结论不代表应用已实现或上线验收已完成。

## 业务和技术主线

编辑保存产品或固定位置的草稿后，线上读数不变。发布人核对资料和修订；校验失败只给出缺项或冲突，成功才一次写入快照、引用、发布指针和日志。一款产品即使出现于多个分类，访客也是从同一个版本读到内容。恢复历史版只生成新草稿，不撤回已经上线的版本。

一套 FastAPI 服务支撑两端，按入口分开授权。批量发布复用单款操作，不引入跨款事务或队列。固定位置只需现有条目的一项唯一约束，不再维护一张绑定表。PC 预览复用展示组件而不复用公开取数路径。见[后端执行流程](design/backend.md#状态并发与执行流程)和[前端复用约定](design/frontend.md#frontend-reuse-decisions)。

## 数据模型评审

### 完整字段定义

以下字段表精确摘自[后端定义](design/backend.md#完整字段定义)，不是已建成的数据库。产品、案例和各配置位置的正文形状及发布条件以同一章节中的正文表为准，不在此另建字段定义。

| 字段 | 类型 | 必填/空值 | 默认值 | 关联/约束 | 证据 |
| --- | --- | --- | --- | --- | --- |
| `content_item.id, kind, live_id, revision, archived_at` | BIGINT、类型、版本 ID、BIGINT、时间 | 线上指针及归档时间可空 | 新建无线上版，修订从 0 起 | 指针只能指向本条目的版本；归档时指针为空；修订在草稿被消费后仍递增 | D-008、D-009 |
| `content_item.config_slot` | VARCHAR(32)，固定位置枚举 | 仅配置条目必填；产品和案例必须为 NULL | 不默认占位 | `CHECK` 按条目类型约束空值和枚举；`UNIQUE(config_slot)` 防止一处多条，产品及案例的 NULL 不占位；固定位置不随编辑变更 | D-022 |
| `draft.item_id, body, edited_by, edited_at` | 条目 ID、JSON、账号 ID、时间 | 均必填，正文可不完整 | 首次编辑才建行 | 每条至多一份；保存、恢复和批量追加共享并发检查 | PRD §3.6 |
| `release.id, item_id, seq, source_revision, body, actor_id, created_at` | BIGINT、关联 ID、整数、修订、JSON、账号 ID、时间 | 均必填 | 发布时生成 | `(item_id,seq)` 与 `(item_id,source_revision)` 唯一；发布后不更新 | D-009、D-015 |
| `directory_node.id`；目录配置正文 `nodes` | 稳定位置 ID；节点序列 | 节点 ID 必填，根的父 ID 可空 | 企业自行配置 | 目录快照保存位置 ID、父 ID、层级、名称、图标、次序、启停；同一树不成环、无失联子节点，改名不换 ID | PRD §3.2 |
| `draft_place(item_id,node_id)`；`release_place(release_id,node_id)` | 两列关联 ID | 必填 | 空集合 | 各自组合主键；版本保留原位置身份；展示时只采用当前已发布且路径有效的位置 | D-014 |
| `asset.id, storage_key, mime, bytes, created_by, created_at` | ID、相对键、媒体类型、大小、账号、时间 | 必填 | 上传生成新键 | 键唯一、不可覆盖；不接受客户端指定路径 | D-006 |
| `release_asset(release_id,asset_id)` | 两列关联 ID | 必填 | 从快照正文抽取 | 组合唯一，含嵌套海报、服务卡、目录图标等；草稿上传不产生公开引用 | D-013 |
| `account.id, login, password_hash, enabled, can_edit, can_publish, can_manage, must_change_password` | ID、登录名、口令摘要、布尔值 | 均必填 | 新账号不隐含授权 | 登录名唯一；发布权仅授予编辑；初始管理员强制改密 | D-007、D-011 |
| `session.token_hash, account_id, expires_at` | 摘要、关联 ID、时间 | 必填 | 登录生成 | 不持久化明文令牌，注销时失效 | D-007 |
| `audit.id, actor_id, action, target_kind, target_id, occurred_at, details, request_key` | ID、账号、动作、目标类型及 ID、时间、JSON、请求号 | 请求号仅发布必填 | 关键操作产生 | 记录关联版本、修订、结果或权限变化；发布键唯一，绑定操作者、动作、对象和修订；删除草稿不级联删日志 | D-015、PRD §4.3 |

## 状态、并发和执行流程

保存和发布都校验期望修订，不能用旧请求覆盖后来保存的稿件。恢复覆盖已有草稿时也需核对目标和修订；重新发布时另查发布权。数据库把版本、公开指针和审计放在同一次提交中。如果提交后断开连接，回到后台按原请求号核对或重试；曾提交的款不能多发，尚未发起的款保持原状。见[事务与失败收束](design/backend.md#状态并发与执行流程)、[WF-003 和 WF-005](design/frontend.md#business-workflows)。

## 前端方案

移动端沿用四页定稿的布局与交互；PC 以正式稿为视觉依据，后台导航、内容列表和状态不与 H5 混用。对照[组件映射](design/frontend.md#ui-组件树与-figma-解析映射)及[视觉检查](design/frontend.md#visual-checks)，抽查窄屏安全区、首页长图轮播、目录计数和服务图原比例。静态稿不作为运行证据。

重点看预览的三个终态：参数无效不请求、修订过期展示冲突、切换后只接受当前目标的响应。用同一展示组件并不意味着共享权限或状态。见[路由契约](design/frontend.md#组件路由与-api-模块)、[状态管理](design/frontend.md#状态管理)。

## 主要风险、迁移、发布和验证

### 主要风险

| 具体失败场景 | 影响 | 预防或处理 | 设计依据 |
| --- | --- | --- | --- |
| 旧预览或迟到响应接管当前画面 | 运营误把别的内容当成将发布的修订 | 阻止无效目标入场，按条目、修订和请求匹配渲染。 | [WF-013、WF-014](design/frontend.md#business-workflows) |
| 私有图未授权仍能读取，或撤下后缓存继续供图 | 草稿或已撤资料泄露 | 逐请求核对当前授权与引用，按公开和私有边界检查缓存。 | [媒体权限](design/backend.md#接口权限与兼容边界) |
| 发布掉线后回执不明 | 误报成功、误补发或重复版本 | 按原请求号查结果，重试不重复写入；未发起款仍不发布。 | [后端验证](design/backend.md#验证方案) |
| 数据库与图片备份失配 | 能恢复记录却打不开旧图 | 同一恢复点备份库和文件，在隔离部署用历史版核对。 | [恢复安排](design/backend.md#风险迁移发布回滚与监控) |

板块内搜索不增建投影，单机素材不另建媒体服务，逐款发布复用单条事务。其运行边界不是样例数量：要能完成代表性查询、素材上传与一致备份，以及页面保持打开时的合格批次。只有反复失败且证据分别指向扫描、磁盘或逐款请求，才先检查现有查询、卷或执行路径，再按[既定升级方向](design/backend.md#风险迁移发布回滚与监控)评估是否拆分。V1 仍不承诺关页后续发。

### 迁移与发布

首版在新库核对迁移结果。后续升级先在恢复副本演练 Alembic 迁移，再在明确窗口改表，不靠容器启动时改表。先发布兼容 API，再更新静态入口。回退前核对数据库版本：兼容时可退应用，不兼容时隔离写入后协调库、文件与对应应用的恢复。上线后监测磁盘、备份年龄、上传和事务错误。见[后端发布与回滚](design/backend.md#风险迁移发布回滚与监控)、[前端发布边界](design/frontend.md#风险迁移发布回滚与监控)。

### 验证清单

- [ ] [固定位置、发布校验](design/backend.md#验证方案)：重复占位被拒；删长图可存草稿不可发布，错类型不能存；H5 仍读旧版，补齐才在两处同步更新。
- [ ] [私有资源与撤权](design/backend.md#验证方案)：仅账号管理权不能读私有内容；编辑可读关联图但不能读同事未关联的图；匿名最后引用撤下后不再可读。
- [ ] [恢复与预览](design/frontend.md#business-workflows)：编辑只恢复草稿。旧修订不渲染；切到乙后放行甲的响应，仍只显示乙。
- [ ] [批量中断](design/frontend.md#business-workflows)：分别核对已提交与未发起的款项，已提交款不重复写入，未发起款不自动续发。
- [ ] [交付与简化边界](design/backend.md#风险迁移发布回滚与监控)：第二企业独立配置；实测代表性查询、上传与批次，记录重复失败的证据；异机恢复后同时核对发布版、草稿及历史图。
- [ ] [实现自审](design/backend.md#验证方案)、[前端自审](design/frontend.md#验证方案)：用应当失败的用例守住边界；核对公开对象的契约及关键说明与实际权限、事务、修订和失败处理一致。

## 评审顺序与抽查路径

1. 先看[私有权限](design/backend.md#接口权限与兼容边界)和[预览状态](design/frontend.md#状态管理)：最容易误把已保存的私有资料当作可公开读取的内容。
2. 再看[数据模型](design/backend.md#数据模型)与[发布流程](design/backend.md#状态并发与执行流程)：核对一个位置只有一个入口，草稿缺项、重复确认都不会改错线上版本。
3. 最后按[业务工作流](design/frontend.md#business-workflows)、[风险和恢复](design/backend.md#风险迁移发布回滚与监控)核对可观察证据：重点区分旧修订、迟到响应、已提交与未发起款，以及异机恢复的实际可读性。
